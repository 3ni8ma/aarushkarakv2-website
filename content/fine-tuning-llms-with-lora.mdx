## Why Full Fine-Tuning Is Usually Overkill

When you fine-tune a language model, you are updating its weights to perform better on a specific task. Full fine-tuning updates every parameter in the model. For a 7B model with float16 weights, that is 14GB of parameters just for the model, plus gradients, optimizer states, and activations during training.

The insight behind parameter-efficient fine-tuning (PEFT) is that most of the model's knowledge does not need to change for a new task. The base model already knows language, reasoning, and world knowledge. What needs to change is how the model applies that knowledge to a specific task. LoRA formalizes this intuition: instead of updating all weights, you freeze the original model and train small adapter matrices that modify the model's behavior.

## How LoRA Works: Low-Rank Decomposition

LoRA decomposes the weight update into two low-rank matrices. Instead of updating a weight matrix W of shape (d, d), LoRA trains two matrices A of shape (d, r) and B of shape (r, d), where r is the rank — typically 4, 8, or 16. The update is W + A @ B, but only A and B are trained.

The math is straightforward: a rank-8 decomposition of a 4096x4096 weight matrix uses 8,192 parameters instead of 16,777,216 — a reduction of over 2000x. The key assumption is that the weight update needed for a specific task has low intrinsic rank: most of the important changes can be captured in a small number of dimensions.

This assumption holds empirically across many tasks. The reason is that fine-tuning is not teaching the model new knowledge — it is adjusting how existing knowledge is applied. That adjustment is inherently low-rank because it is a small perturbation to a model that already works.

## Implementing LoRA with PEFT

The Hugging Face PEFT library makes LoRA straightforward. The core workflow is: load a base model, define which layers to adapt, configure LoRA parameters, and train.

The critical choices are: which layers to apply LoRA to (attention projections are most common, but FFN layers also benefit), the rank (higher is more expressive but uses more memory), and the alpha scaling factor (controls the magnitude of the LoRA update relative to the base weights).

A common configuration is rank 16, alpha 32, applied to all attention projection layers (q_proj, k_proj, v_proj, o_proj). This typically uses 1-3% of the memory of full fine-tuning while achieving 90-95% of the performance on most tasks.

## Data Preparation: The Part That Actually Matters

The quality of your training data determines the quality of your fine-tuned model more than any hyperparameter. I have seen models trained on 500 carefully curated examples outperform models trained on 10,000 noisy ones.

The format matters. For instruction-tuning, the standard format is a system prompt, a user message, and an assistant response. Consistency in formatting prevents the model from learning conflicting patterns. If some examples use '### Instruction:' and others use 'User:', the model wastes capacity learning to handle both formats instead of learning the task.

Data diversity matters more than data volume. If every example in your training set asks the model to classify sentiment, the model will learn sentiment classification but forget everything else. Include examples that test different capabilities: reasoning, formatting, edge cases, and multi-step tasks.

## Training Loop: What to Watch For

LoRA training has failure modes that differ from full fine-tuning. The most common is catastrophic forgetting: the model learns the new task but loses capabilities it had before. This happens when the learning rate is too high or the training set is too narrow.

The learning rate for LoRA is typically higher than for full fine-tuning — 1e-4 to 5e-4 is common — because the adapter matrices are randomly initialized and need larger updates to converge. But higher learning rates increase the risk of forgetting. The balance is delicate.

Monitoring validation loss is necessary but not sufficient. A model can have low validation loss and still produce worse outputs than the base model on general tasks. I evaluate fine-tuned models on both the target task and a set of general benchmarks to catch regression.

## Merging and Deploying LoRA Adapters

The trained LoRA adapter is small — typically 10-100MB for a 7B model. It can be stored separately from the base model and loaded on demand. This enables serving multiple fine-tuned variants from a single base model, switching adapters based on the request.

Merging the adapter into the base model produces a standalone model with no LoRA overhead. The merge is a single matrix operation: W_merged = W_base + A @ B. After merging, the model runs at the same speed as the original — there is no inference overhead from LoRA.

The tradeoff is flexibility versus simplicity. Keeping adapters separate lets you switch tasks dynamically but requires managing multiple files. Merging produces a simpler deployment but locks the model to one task.

## Lessons I Learned the Hard Way

My first LoRA experiment failed because I applied adapters to every linear layer in the model. The adapter count was in the hundreds, and the training was slower than full fine-tuning — the opposite of the point. The lesson was that LoRA's efficiency comes from selective application, not blanket coverage.

The second lesson was about evaluation. I measured success by validation loss and declared the experiment a success. Then I deployed the model and discovered it had forgotten how to format code. The validation set did not include code tasks, so the regression was invisible. Now I always evaluate on a broad benchmark suite before deploying.

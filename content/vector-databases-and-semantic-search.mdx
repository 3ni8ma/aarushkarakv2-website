I built a search engine that could not find the word 'car' in a document about 'automobiles'. The keyword search returned zero results because the strings do not match. The document was right there, full of relevant information, and the search engine was blind to it. That failure led me to vector databases and semantic search — a fundamentally different way of finding information that understands meaning instead of matching characters.

## Why Keyword Search Hits a Wall

Traditional search engines work by matching tokens. You index documents by splitting them into words, counting frequencies, and building an inverted index. When a query arrives, you look up which documents contain the query terms and rank them by relevance scores like TF-IDF or BM25.

This works remarkably well for exact matches. But it fails when the query and the document use different words for the same concept. 'Automobile' and 'car' are semantically identical but lexically different. 'How to fix a broken heart' and 'emotional recovery after a breakup' describe the same topic with completely different vocabulary.

The fundamental limitation is that keyword search operates on the surface form of text, not its meaning. To search by meaning, you need a representation of text that captures semantics — and that is exactly what embeddings provide.

## Embeddings: Converting Meaning to Vectors

An embedding is a dense vector representation of text that captures its semantic meaning. Similar texts produce similar vectors, regardless of the specific words used. The embedding model learns to map 'car' and 'automobile' to nearby points in a high-dimensional space.

Modern embedding models are transformer-based neural networks trained on massive datasets. They learn to predict which sentences appear together, which paraphrases have the same meaning, and which texts answer the same question. The resulting vectors encode syntax, semantics, and even world knowledge.

The dimensionality of these vectors is typically 384 to 1536. Each dimension does not correspond to a human-interpretable concept — the representation is distributed across all dimensions. But the geometry is meaningful: the cosine similarity between two vectors approximates their semantic similarity.

## Vector Databases: Indexing for Similarity

A vector database stores embeddings and answers similarity queries: given a query vector, find the k most similar vectors in the database. This is fundamentally different from traditional databases, which answer exact-match queries.

The naive approach — computing the cosine similarity between the query and every vector in the database — works but does not scale. With a million vectors of dimension 1536, each query requires 1.5 billion floating-point operations. Vector databases use approximate nearest neighbor (ANN) algorithms to make this practical.

The most common ANN algorithm is HNSW (Hierarchical Navigable Small World). It builds a graph where each vector is connected to its nearest neighbors, then searches the graph greedily. HNSW achieves sub-millisecond query times on millions of vectors with recall above 95%. Other algorithms like IVF (Inverted File Index) partition the space into clusters and only search within nearby clusters.

## Building a RAG Pipeline

Retrieval-Augmented Generation (RAG) combines vector search with language model generation. The pipeline is: embed the user's query, retrieve the most relevant documents from the vector database, and pass those documents as context to a language model for generation.

The key advantage of RAG is that it grounds the language model in specific, verifiable information. Instead of generating answers from parametric memory (what the model learned during training), RAG generates answers from retrieved documents (what the database contains). This reduces hallucination and allows the model to answer questions about information it was not trained on.

The implementation details matter. Chunking strategy determines how documents are split into segments. Overlap between chunks prevents information from being lost at boundaries. Metadata filtering allows combining semantic search with structured filters (date, category, author). Reranking the retrieved results with a cross-encoder improves precision at the cost of latency.

## Chunking Strategy: The Hidden Variable

How you split documents into chunks affects retrieval quality more than most people realize. Split too small and you lose context — a chunk containing just 'the answer is 42' is meaningless without the question. Split too large and you dilute relevance — a 5000-word chunk about machine learning is not specific enough to answer a question about LoRA fine-tuning.

The sweet spot depends on the content type. For technical documentation, 256-512 tokens with 50-100 tokens of overlap works well. For conversational content, smaller chunks (128-256 tokens) preserve the back-and-forth structure. For academic papers, chunking by section preserves the logical structure.

Semantic chunking — splitting at natural topic boundaries rather than fixed token counts — produces the most coherent chunks but requires a more sophisticated implementation. The basic approach is to compute embeddings for each sentence, then split where the cosine similarity between consecutive sentences drops below a threshold.

## Evaluation: Measuring What Matters

The standard metrics for vector search — recall@k, precision@k, and mean reciprocal rank — measure retrieval quality. But retrieval quality is not the same as end-to-end quality. A system with 95% recall can still produce wrong answers if the language model misinterprets the retrieved context.

I evaluate RAG systems on three levels: retrieval quality (are the right documents found?), answer quality (does the model produce correct answers from the retrieved context?), and faithfulness (does the answer actually come from the retrieved context, or is it hallucinated?).

The most useful evaluation metric is faithfulness: given the retrieved context, can the model's answer be verified against it? This catches both retrieval failures (wrong documents) and generation failures (correct documents, wrong interpretation).

## What I Learned the Hard Way

My first vector database used a naive chunking strategy: split every document into 500-token chunks with no overlap. The result was that questions about concepts that spanned chunk boundaries returned irrelevant chunks. The fix was adding 100-token overlap between chunks, which increased the index size by 20% but improved retrieval quality by 35%.

The second lesson was about embedding model selection. I started with a general-purpose embedding model and got mediocre results on technical content. Switching to a model fine-tuned on technical documentation improved retrieval quality by 20% with no other changes. The embedding model is the most important component in the pipeline, and it is the one most people spend the least time choosing.
